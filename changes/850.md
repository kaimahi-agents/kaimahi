### Fixed

- `kmx cluster orka install` no longer reports a reused Orka installation as running from a Deployment status written before a node restart. Offline install and reuse, and online reuse (including the Orka step of `kmx cluster up`), now wait up to 10 minutes until each required Deployment's pods are Running and Ready on the pinned images, owned by that Deployment through their ReplicaSet's UID, and Orka's typed `/readyz` answers `status: ok` through its API Service. On the selected kind cluster (context `kind-<KIND_CLUSTER>`) the pods' Ready transition and container starts must also be no older than the node container's current start. The wait only reads; the Service check needs `get` on `services/proxy` in `orka-system`. Foreign pods and ReplicaSets, scaled-to-zero workloads, a missing or ambiguous API Service and the API server's own denial of a read refuse as soon as they are observed; offline also refuses execution settings that change while waiting, and online reuse refuses a controller that is being deleted, replaced under any name or stops being the pinned image while waiting. The `kmx cluster up` preflight still reads Deployment status once, so a status that already shows the controller unready refuses there before the Orka step's wait.
